# 束线快门联锁认证工作台（离线纯前端）

同步辐射束线调试前，用于确认快门开闭组合不违反联锁规则的纯前端工作台。
TypeScript + React + Vite 实现编辑与展示，全部计算在浏览器内完成，运行时不联网；
Docker Compose 提供名为 `web` 的静态页面服务。

## 语义模型

- 每个快门取 `OPEN` / `CLOSED` 两态；每条二元规则由两个文字组成，含义为**至少一个成立**（析取子句 `a ∨ b`）。
- 规则 `a ∨ b` 等价于两条蕴含：`¬a → b`、`¬b → a`，据此构建**蕴含图**。
- 临时锁定快门为 `l` 等价于加入单位子句，即蕴含边 `¬l → l`。
- **可行性裁决（精确 2-SAT）**：Tarjan 强连通分量。某快门的 OPEN、CLOSED 两个文字落在同一 SCC ⇔ 无解。
- **字典序最小方案**：快门按 **ID 的 UTF-8 字节序**排列，逐变量优先尝试 `CLOSED`，
  将候选值作为单位边加入后重算 SCC，可扩展则固定（前缀 + 候选可满足），否则取 `OPEN`。
  这保证返回的完整方案是「CLOSED 优先」字典序中最小的可行赋值。
- **冲突见证**：无解时选取所有“正反文字同 SCC”的快门中 **UTF-8 字节序最小**的 ID，
  在其 SCC 内分别求出 `OPEN → CLOSED` 与 `CLOSED → OPEN` 两条蕴含路径，
  路径每一步都标注来源规则序号与原文（或锁定），可逐条复核形成闭环。
- **锁定修复建议**：规则本身可满足、仅因值班员临时锁定导致无解时，若当前锁定数 **≤ 8**，
  对完整规则与锁定集合枚举锁定子集，求**精确最少撤销数**；并列时按快门 ID 的 UTF-8
  字节序选择撤销清单，撤销后的字典序最小完整方案仍由原 2-SAT 求解器给出。
  唯一修复手段是「撤销锁定」——不修改规则、不翻转锁定值、不套用旧快门表。
  若全部解锁后规则仍无解，明确报告**规则自身冲突**，不提供任何建议；
  锁定数超过 8 时不做指数级枚举，仅提示锁定过多。
- **新增候选规则预检**：新增一条二元规则前，复用导入解析（与整份导入共用同一行解析器）
  与同一套 2-SAT 语义在**临时视图**上裁决，工作区（规则、锁定、快门表、认证结论、导出）
  一律不变。四类结论：
  - **原工作区已冲突**：当前规则 + 锁定本就无解——沿用当前蕴含图的冲突闭环见证
    （只含原规则 / 锁定边），明确标注与候选无关，不把旧冲突归咎于新规则；
  - **候选导致冲突**：当前可行、加入候选后无解——给出含候选规则边的冲突闭环，
    并附一份原锁定下可行的方案，证明矛盾确由候选引入；
  - **候选冗余**：当前可行方案全部已满足候选（被原规则 + 锁定蕴含，或被锁定强制），
    新增不排除任何快门组合；
  - **候选有效收紧**：存在违反候选的可行赋值——返回一份**满足候选的规范方案**
    （加入候选后的 CLOSED 优先字典序最小完整方案）与一份**违反候选的可复核见证**
    （把候选两个文字同时取反作为临时单位，在原规则 + 原锁定下求得的字典序最小完整方案），
    两份方案都遵守全部原锁定，并标出被排除的组合（两文字同时不成立）。
- **预检与确认隔离**：确认新增只允许基于**尚未变化**的工作区——预检快照记录当时的
  规则/锁定版本与候选草稿；任何导入、锁定编辑、规则确认或草稿改动都使旧预检**立即过期**，
  过期预检不可确认。确认把候选追加为末条规则（序号与预检临时视图一致），认证结论不自动重算、
  采纳/导出状态清除，沿用既有「规则变化须重新认证」语义。原认证及锁定修复流程不变。


## 导入格式与校验

```
[shutters]
快门ID          # 每行一个，2–300 个，ID 唯一且不含空白、不得为 OPEN/CLOSED
...
[rules]
ID1 OPEN  OR ID2 CLOSED     # OR 可省略；空行与 # 注释忽略
...
```

规则按记号位置解析：首两个与末两个记号为两个文字，中间记号（若有）须全部为连接词
`OR`（大小写不敏感）。因此 `OR`、`__proto__`、`constructor`、`toString` 等均可作为
普通快门 ID，在导入、规则判定、手工锁定、求解预览与导出中保持同一身份与状态。

规则最多 3000 条。出现**未知 ID、重复快门（声明重复或同规则内重复）、非法状态、
记号数量错误、小节缺失、越界**等任何问题时，**整份导入被拒绝**，页面保留当前工作区不变，并列出全部错误行。

## 操作流程

1. 粘贴文本或「载入示例」→「校验并导入」。
2. 在快门表中编辑当前状态；点「锁定」可临时锁定某快门（再点按钮可切换锁定值/解锁）。
3. 「运行认证」：
   - 可行 → 展示可直接执行的快门表（字典序最小完整方案）与相对当前表的改动列表；
   - 无解 → 展示最小矛盾快门及两条可逐条复核的冲突闭环，不提供执行稿；
     同时给出锁定修复建议（最少撤销清单 + 撤销后的候选方案，确认前不生效）。
4. 规则或锁定一旦变化，旧预览与修复建议**立即标记失效**，必须重新认证；
   过期建议不能采纳、不能导出，也不会改写工作区。
5. 「确认修复」只在建议有效时可用：一次性撤销所列锁定并自动重新认证，
   规则、快门表与其余锁定一律不动。
6. 「新增规则预检」：输入一行候选规则（与导入同一语法、同一校验）→「预检候选规则」，
   区分原工作区已冲突 / 候选导致冲突 / 候选冗余 / 候选有效收紧；收紧时对照
   「满足候选的规范方案」与「违反候选的可复核见证」。预检不改工作区；
   导入、锁定编辑或草稿修改会立即使预检过期，过期不能「确认新增」。
   确认后规则追加为末条、须重新认证；原认证与锁定修复流程不变。
7. 「采纳方案」将结果写入快门表；「下载采纳稿」导出 UTF-8 文本，
   内容按 UTF-8 字节序逐行 `ID STATE`，与屏幕表完全一致。改动快门表会清除采纳状态。

## 本地开发

```bash
npm install
npm run dev        # http://localhost:5173
npm run build      # 类型检查 + 生产构建到 dist/
npm run preview    # 预览生产构建 http://localhost:4173
```

## Docker Compose（服务名 web）

```bash
docker compose up --build -d
# 浏览器访问 http://localhost:8080
```

多阶段构建：Node 构建静态资源 → nginx 仅托管 `dist/`，无任何外网运行时依赖。

## 测试

```bash
npm test                       # Vitest：小规模穷举 + 随机交叉 + 性能
npm run e2e:install            # 首次运行安装 Playwright Chromium
npm run e2e                    # Playwright：仅一条端到端主流程
```

- **Vitest（`src/core/*.test.ts`）**
  - 对 n=2 的全部规则子集 × 全部锁定组合，以及 n=3 的 12 种合法候选规则的大量子集 × 锁定组合做穷举；
  - 期望值来自**独立的暴力枚举 oracle**（枚举全部 2ⁿ 个赋值，取 CLOSED 优先字典序下首个可行解；
    矛盾判定使用独立的 Warshall 可达闭包，而非求解器的 Tarjan）；
  - 见证路径逐边校验：必须是蕴含图中的真实边，且每步指回真正蕴含它的原规则；
  - 锁定修复建议：n=3 全部规则子集 × 全部 27 种锁定组合穷举，与独立 oracle
    （枚举全部锁定子集）核对精确最少撤销数与并列裁决；另有 UTF-8 字节序并列、
    规则自身冲突、锁定上限（8）、特殊 ID 等定向用例；
  - 候选规则预检：n=2 全部 16 种规则子集 × 全部 9 种锁定组合 × 4 种候选全量穷举，
    以及 n=3 抽样规则子集 × 锁定组合 × 12 种候选，按独立暴力赋值 oracle 核对四类结论；
    收紧时逐字段核对规范方案与违反见证（均遵守原锁定、分别满足 / 违反候选），
    冲突见证逐边校验且旧冲突路径不含候选规则边；另含预检/确认隔离状态机、
    3000 规则上限、解析边界（未知 ID / 非法状态 / 同规则重复 / OR 错位）、特殊 ID 用例；
  - 另有 120 个确定性随机实例交叉验证，以及 300 快门 / 3000 规则上限规模的完整性与性能检查。
- **Playwright（`e2e/main-flow.spec.ts`）**：只走一次主流程——
  非法导入整份拒绝 → 示例导入 → 认证得到最小方案与改动 → 双锁触发无解闭环并逐规则复核
  → 解锁恢复 → 采纳 → 下载文件逐行断言与屏幕一致。期望结果均由求解器逻辑决定，无固定假结论、无占位按钮。
- **Playwright（`e2e/lock-repair.spec.ts`）**：锁定修复建议——
  无解给出最少撤销清单与候选方案 → 期间改动锁定使建议过期（过期建议不改写工作区、
  不可采纳或导出）→ 重新认证得到基于当前锁定的新建议 → 确认修复一次性撤销所列锁定并
  重新认证 → 采纳 → 下载一致；另有规则自身冲突与锁定超限两条支线。
- **Playwright（`e2e/candidate-precheck.spec.ts`）**：新增规则预检与确认隔离——
  有效收紧（规范方案 / 违反见证均遵守原锁定，预检不改工作区）→ 草稿与锁定改动立即使
  预检过期、拒绝确认 → 重新预检后确认追加并须重新认证；另覆盖导入替换清空白检、
  候选导致冲突（见证含候选边、禁止确认）、原工作区已冲突（旧见证不归咎候选）、
  候选冗余与候选解析失败五条支线。
